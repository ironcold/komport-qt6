## Verdict

**Amend before adoption.** The re-cut fixes the timing conflict and substantially improves the split, but the §5.11 phase model still cannot safely govern an interrupted multi-event synchronous step. Completion/`stop()` ordering also remains under-specified.

## New findings

1. **BLOCKER — a synchronous multi-event step has no authorized post-signal continuation.** Steps may synchronously emit multiple events ([§5.6:605](/home/max/Development/misc/komport-qt6/docs/specs/SPEC-M10-session-reader-passive-replay.md:605), [§5.6:621](/home/max/Development/misc/komport-qt6/docs/specs/SPEC-M10-session-reader-passive-replay.md:621)). After any non-final emission, a receiver may `play()`, `start()`, `close()`, or otherwise supersede the state. `Continue` cannot authorize a resumed step because it requires `Playing`; `Finish` cannot authorize it because it requires the captured end. Add a phase/rule for continued step delivery and a test where the first delivery of a multi-event step is interrupted.

2. **BLOCKER — final-delivery `stop()` has no complete signal contract.** The `Complete` token exception correctly covers a token bump during the delivery receiver, but not the full externally observable sequence. Specify whether `stateChanged(Paused)` occurs, the exact returned stop report, and what a `stop()` from `stateChanged(Finished)` does before `replayFinished` is emitted.

3. **HIGH — cancellation ordering remains invented rather than specified.** The token is “bumped by every operation that cancels one” ([§5.11:945](/home/max/Development/misc/komport-qt6/docs/specs/SPEC-M10-session-reader-passive-replay.md:945)), while `Cancel` requires token equality ([§5.11:978](/home/max/Development/misc/komport-qt6/docs/specs/SPEC-M10-session-reader-passive-replay.md:978)). The implementation needs a specified ordering—authorize/cancel before bump, or bump then use an explicitly refreshed cancellation snapshot—especially for a `stop()` called inside an emission.

A1 is otherwise cleanly separable: §5.5/§5.6 state the valid-mutation-context precondition and do not require identity, snapshot, or guards in 3a ([§5.5:532](/home/max/Development/misc/komport-qt6/docs/specs/SPEC-M10-session-reader-passive-replay.md:532)). The unscoped §6 delivery-boundary invariant should be qualified before using the two-slice gate to claim there is no hidden re-entrancy semantics.

I reviewed the specification text and prior review record read-only. I did not review an implementation or execute tests.
